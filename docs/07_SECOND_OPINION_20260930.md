## 1. 外部意见原文要点

### 1.1 三问结论表（外部给出）

| 问题 | 选择 | 判断 |
|---|---|---|
| 1. 3586 行控制台 | **A：原生 JS + ES modules** | 不引 Vue/Vite |
| 2. 4 个设置 | **拆分处理，主体选 B，但不是四项全 B** | 服务端口径集中，扩展运行参数本地缓存 |
| 3. 4000 行 Puppeteer 链 | **A：围栏冻结** | 不删除、不继续维护 |

### 1.2 Q1 数字与理由

> 估计：把 3586 行单文件拆成 8–12 个 ES module，后续维护成本可下降约 **20–35%**；首次拆分本身大约 **4–8 小时**。**置信度 0.88**。
>
> 理由很直接：你现在的问题是"单文件过大"，不是"缺少前端框架能力"。
>
> 引 Vue/Vite 后会额外引入：组件模型 / 响应式状态 / 构建链 / 依赖升级 / SEA 打包兼容验证。而你的硬约束恰好是"不想增加构建复杂度 + 静态 import + 存量代码不能大改"。所以这里引框架解决的是架构风格问题，不是当前瓶颈。

### 1.3 Q2 拆分方案（**这是外部意见最有价值的一条**）

> 不是纯 A/B/C 三选一；我会选"**B 为服务端真源 + A 为扩展本地运行参数**"。具体拆：
>
> | 键 | 归属 | 理由 |
> |---|---|---|
> | `serverBase` | 扩展自己的连接配置 → `storage.local` | 回环地址，扩展自己才知道 |
> | `pollIntervalSec` | 扩展自己的运行参数 → `storage.local` | 扩展自己调度 |
> | `commuteMode` | **服务端业务输入 → 服务端 config 真源** | 实际参与服务端计算 |
> | `oneWayKm` | **服务端业务输入 → 服务端 config 真源** | 实际参与服务端计算 |
>
> 预计可消除"三处真源"造成的 **2/3 左右配置漂移风险**；**置信度 0.93**。
>
> 尤其是 `commuteMode`/`oneWayKm`：既然实际参与服务端计算，就不应该由扩展 `storage.local` 成为业务真源。否则非常容易出现"扩展显示 5km / 服务端实际 8km / 控制台 3km"，**而且测试可能仍然全绿，因为测试直接调用服务端私有方法**。
>
> **不要双写。** 双写只是把"多个真源"变成"多个真源 + 同步一致性问题"。

### 1.4 Q3 与「真冻结」的定义

> 选 A，但"冻结"必须是真冻结。4000 行旧 Puppeteer 链不要删，但也不要维持现状。建立明确的 `legacy/auto-apply/` 或类似隔离目录，做到：
> 新主链路 → 绝不 import legacy → legacy 只读保存 → **不参与构建/运行**。
>
> 预计删除它会损失**数百到上千行**值得保留的选择器/DOM 经验；但继续让它参与主工程维护，后续每次改动都会增加约 **10–20%** 的认知/回归负担（**置信度 0.78**）。
>
> 你已经有一个非常有价值的事实：31 次打招呼 → 3 回复 → 0 面试，而且账号硬封。所以"自动投递机制"本身已被实证淘汰。但是：招聘网站 DOM 结构 / 选择器 / 岗位字段提取 / 聊天内容结构 / 页面行为观察 —— 这些仍然是知识资产。
> **保存知识，废弃机制。**

### 1.5 元问题一：这套并行顺序最可能死在哪一步（**外部否决了我们的一个关键决策**）

> 不是 6 个子代理同时写代码。真正危险的是：**"契约层冻结"太早**。
>
> 最大的风险是第一个箭头（先定契约 → 冻结）。
>
> 这意味着现有行为本身就是隐含契约：26 个私有方法被测试直接调用 / 11 套测试 / 3586 行控制台 / 三处配置真源 / 扩展轮询 / 服务端业务输入 / 旧代码里的真实数据判据。
>
> 如果先设计一个"干净的新契约"，6 个代理会很容易各自实现一个合理模块，最后才发现：A 的字段定义 ≠ B 的字段定义 ≠ 现有测试期待 ≠ 扩展实际 payload。然后最后串行搬存量代码时才发现接口不兼容。
>
> 顺序应改为：**现存行为取证 → 列出真实输入/输出/副作用 → 契约 v0 → 6 个代理并行 → 契约变更集中收口 → 最后迁移**。
> 尤其先做一份 **Compatibility Matrix**：模块 / 当前入口 / 当前输入 / 当前输出 / 被谁调用 / 测试覆盖 / 准备保留-修改-废弃。**这比先写漂亮的接口定义重要得多。**
>
> 我只改一个关键点：**不要"先冻结契约"，而要"先冻结事实，再冻结契约"。**

### 1.6 元问题二：三个明显容易踩的坑

1. **配置面变成隐形分布式系统**。三个载体（EXE 内嵌 `.env` + server config / Chrome Extension `storage.local` / Web Console 表单 state）若不先定义"谁是真源、谁只是缓存、谁可以修改、修改后谁通知谁"，代理越多问题越严重。
2. **26 个私有方法被测试直接调用**。不要趁模块化顺手把它们"修漂亮"。应当把它们当成**暂时存在的 ABI**：旧私有方法 → 兼容 facade → 新模块。否则"最后串行搬迁"会变成"最后同时修代码 + 修测试 + 修契约"。
3. **5 秒轮询的并发重入（全新问题，我们的 06 文档里没有）**。扩展每 5 秒 POST 一次，若服务端某次处理超过 5 秒：
   ```
   t=0   request A
   t=5   request B
   t=10  request C
   ```
   若 A/B/C 对同一岗位或聊天上下文没有幂等控制，就会出现重复计算、响应乱序、**旧建议覆盖新建议**。建议至少有 `requestId` / `jobId`|`conversationId` / `timestamp`，以及服务端的去重/过期判断。

### 1.7 外部强调的原则（已并入裁决）

> 最关键的不是"发现所有错误"，而是让 DSH 宁可报 `UNCERTAIN`，也不要把异常网页状态当成正常第二意见。

## 3. 对 06 文档的修订（本次实际改动）

1. **§7 配置单一真源 → 改为两级真源表**：`serverBase` / `pollIntervalSec` 归扩展 `storage.local`（扩展自有运行参数）；`commuteMode` / `oneWayKm` 归服务端 `config/`（业务真源）。扩展启动只**只读拉取业务配置**用于显示，**不写回**。删掉"四项全走 `/api/config`"的表述。
2. **§8 执行分期新增 P0.0**：现状取证 → Compatibility Matrix → 再冻结契约。
3. **§3.2 禁止清单新增两条可自动检出项**：轮询请求必须带 `requestId`/`conversationId`/`timestamp`；响应必须带 `schemaVersion` 且服务端丢弃过期请求的结果。
4. **§6 围栏补记**：围栏的定义改为"运行期不可达 + 改动即失败"，并写明为什么不采用物理隔离目录（B1 的硬约束论证）。
5. **§3.4 补记 ABI 措辞**：26 个私有方法在 P3 完成前视为临时 ABI，"最后串行搬迁"不得与"修测试/修契约"混在同一步。
